# راهنمای کاهش ریسک آسیب‌پذیری‌های PHP2Shell در PHP و Apache قدیمی

این مخزن راهکار پیکربندی برای کاهش ریسک مسیرهای حمله مرتبط با قابلیت `session.upload_progress` در PHP را ارائه می‌کند. اسکریپت فعلی برای Apache با `mod_php` و خانواده بسته‌های EL7 طراحی شده است.

> **مهم:** غیرفعال‌کردن `session.upload_progress` یک mitigation یا اقدام کاهشی است؛ patch امنیتی PHP محسوب نمی‌شود و جایگزین ارتقای PHP و سیستم‌عامل به نسخه‌های پشتیبانی‌شده و اصلاح‌شده نیست.

## محدوده و محدودیت‌ها

اسکریپت برای این خانواده بسته‌ها طراحی و در محیط مشابه آن بررسی شده است:

- CentOS 7 و مشتق‌های سازگار با EL7
- خانواده بسته PHP: `php-5.4.16-48.el7`
- خانواده بسته Apache: `httpd-2.4.6-98.el7.centos.7`
- Apache با ماژول `mod_php`

ممکن است توزیع سفارشی نام متفاوتی در `/etc/os-release` داشته باشد، اما همچنان از بسته‌های مبتنی بر CentOS 7 استفاده کند. اسکریپت قبل از تغییر تنظیمات، اطلاعات سیستم‌عامل و خانواده بسته‌های RPM را بررسی می‌کند.

**وضعیت CVEها را نمی‌توان صرفاً بر اساس شماره نسخه PHP به تمام توزیع‌ها و بسته‌ها تعمیم داد.** اصلاحات backport‌شده، تفاوت بسته‌های vendor و پیکربندی اجرا می‌توانند نتیجه را تغییر دهند. همیشه اطلاعیه امنیتی مربوط به همان توزیع و بسته را بررسی کنید.

اسکریپت فایل `/etc/httpd/conf.d/php.conf` را مدیریت می‌کند. این اسکریپت فایل‌های اجرایی PHP را patch نمی‌کند، بسته‌ها را ارتقا نمی‌دهد و جایگزین بررسی امنیتی کل برنامه نیست.

## اسکریپت چه کاری انجام می‌دهد؟

هنگام اجرا با دسترسی `root`، فایل `test.sh` این مراحل را انجام می‌دهد:

1. سیستم‌عامل و خانواده بسته‌های PHP و Apache را بررسی می‌کند.
2. وجود Apache و ماژول PHP آن را بررسی می‌کند.
3. دستورهای فعال `php_admin_value session.upload_progress.enabled` را در `/etc/httpd/conf.d/php.conf` می‌خواند.
4. اگر دقیقاً یک دستور فعال با مقدار `0` وجود داشته باشد، فقط `httpd -t` را اجرا می‌کند و **بدون تغییر فایل، ایجاد بکاپ یا ری‌استارت Apache** خارج می‌شود.
5. اگر دستور وجود نداشته باشد، تکراری باشد یا مقدار دیگری داشته باشد، فایل اصلاح‌شده را آماده می‌کند، از فایل اصلی بکاپ می‌گیرد، پیکربندی را اعتبارسنجی می‌کند و فقط پس از یک تغییر واقعی Apache را ری‌استارت می‌کند.
6. در صورت شکست اعتبارسنجی یا ری‌استارت، تلاش می‌کند بکاپ را برگرداند.
7. در پایان، وضعیت تنظیمات و ارزیابی مربوط به CVEها را گزارش می‌کند.

گزارش اسکریپت، ارزیابی پیکربندی است؛ اسکنر آسیب‌پذیری نیست و ثابت نمی‌کند که سیستم از تمام آسیب‌پذیری‌ها مصون است.

## ارزیابی CVEها

توضیحات زیر به اطلاعیه vendor و خانواده بسته مشخص‌شده محدود هستند و نباید بدون بررسی به بسته‌های دیگر تعمیم داده شوند.

### CVE-2026-109618

طبق ارزیابی منتشرشده از سوی Red Hat، کد آسیب‌پذیر مربوط به مسیر اجرای کد مورد بحث در بسته PHP مربوط به RHEL 7 وجود ندارد؛ بنابراین بسته مورد اشاره در آن اطلاعیه برای این CVE آسیب‌پذیر اعلام نشده است.

- این نتیجه مختص همان vendor و خانواده بسته است.
- تنظیم `session.upload_progress.enabled=0` این CVE را رفع نمی‌کند.
- برای بسته‌های توزیع‌های دیگر، وضعیت را از اطلاعیه امنیتی همان vendor بررسی کنید.

### CVE-2026-109619

برای بسته PHP مربوط به RHEL 7، راهنمای Red Hat غیرفعال‌کردن session upload progress را به‌عنوان اقدامی برای حذف مواجهه مورد بحث در اطلاعیه معرفی می‌کند.

تنظیم PHP:

```ini
session.upload_progress.enabled = Off
```

برای Apache با `mod_php`، اسکریپت از این دستور استفاده می‌کند:

```apache
php_admin_value session.upload_progress.enabled 0
```

این کار قابلیت مرتبط با مسیر حمله گزارش‌شده را غیرفعال می‌کند؛ اما کد PHP را patch نمی‌کند و جایگزین به‌روزرسانی امنیتی vendor نیست.

### CVE-2026-115560

راهنمای vendor مورد استناد، غیرفعال‌کردن session upload progress را برای کاهش ریسک این مورد توصیه می‌کند. دستور Apache بالا این مقدار را در پیکربندی مربوط به `mod_php` اعمال می‌کند.

پیش از اتکا به این نتیجه در سیستم دیگر، اطلاعیه امنیتی مربوط به توزیع و نسخه دقیق بسته را بررسی کنید.

## اجرای خودکار

پیش از اجرا، محتوای `test.sh` را بررسی کنید.

```bash
chmod 750 test.sh
sudo ./test.sh
```

اگر `sudo` نصب نیست، اسکریپت را با کاربر `root` اجرا کنید.

وقتی تنظیم دقیقاً یک بار از قبل اعمال شده باشد، خروجی باید مشابه این باشد:

```text
[OK] Mitigation is already configured exactly once.
Syntax OK
[OK] Apache configuration syntax is valid.
[INFO] No backup created; no file changed; no restart performed.
```

اگر تغییر لازم باشد، اسکریپت یک بکاپ زمان‌دار کنار فایل تنظیمات ایجاد می‌کند، پیکربندی Apache را بررسی می‌کند و فقط در صورت موفقیت بررسی و وجود تغییر واقعی، Apache را ری‌استارت می‌کند.

پس از اجرا، مقدار مؤثر تنظیم را از محیط PHP وب نیز بررسی کنید.

## اعمال تنظیمات به‌صورت دستی

مسیر فایل تنظیمات و روش اعمال مقدار به SAPI مورد استفاده بستگی دارد. روش `mod_php` با PHP-FPM یکسان نیست.

### ۱. شناسایی SAPI و فایل تنظیمات

برای PHP خط فرمان:

```bash
php --ini
php -i | grep -i 'Server API'
php -i | grep -i 'session.upload_progress.enabled'
```

برای مشاهده ماژول‌های Apache:

```bash
httpd -M 2>/dev/null | grep -E 'php.*module|mpm_'
apachectl -M 2>/dev/null | grep -E 'php.*module|mpm_'
```

در Debian/Ubuntu ممکن است دستور `apache2ctl -M` باشد و نام سرویس معمولاً `apache2` است. ممکن است PHP از طریق PHP-FPM اجرا شود، نه `mod_php`.

**مقدار PHP در CLI الزاماً با مقدار PHP وب برابر نیست.** محیط وب را جداگانه بررسی کنید.

### ۲. تهیه بکاپ

برای Apache با `mod_php` در ساختار متداول EL7:

```bash
sudo cp -a /etc/httpd/conf.d/php.conf \
  "/etc/httpd/conf.d/php.conf.bak.$(date +%Y%m%d-%H%M%S)"
```

در Debian/Ubuntu، فایل مرتبط ممکن است زیر `/etc/apache2/` یا مسیر تنظیمات نسخه PHP قرار داشته باشد. مسیر EL7 را بدون بررسی کپی نکنید.

### ۳. افزودن دستور Apache

برای Apache با `mod_php`، دستور زیر را در context مناسب تنظیمات Apache یا PHP قرار دهید:

```apache
php_admin_value session.upload_progress.enabled 0
```

در نصب متداول EL7 با `mod_php`، این دستور می‌تواند در `/etc/httpd/conf.d/php.conf` قرار بگیرد.

قبل از افزودن، وجود دستور فعال و تکراری را بررسی کنید:

```bash
grep -RniE '^[[:space:]]*php_admin_value[[:space:]]+session\.upload_progress\.enabled' \
  /etc/httpd 2>/dev/null
```

دستور `php_admin_value` مخصوص Apache با `mod_php` است. آن را داخل فایل pool مربوط به PHP-FPM قرار ندهید؛ در آن context معتبر نیست.

### ۴. روش جایگزین: تنظیم PHP INI

اگر SAPI و نحوه استقرار شما پشتیبانی می‌کند، در فایل `php.ini` فعال یا فایل INI اختصاصی همان SAPI این مقدار را قرار دهید:

```ini
session.upload_progress.enabled = Off
```

برای PHP-FPM، از روش پیکربندی مورد پشتیبانی نسخه نصب‌شده استفاده کنید و سرویس FPM مربوطه را reload یا restart کنید. فایل pool مربوط به PHP-FPM دستور Apache یعنی `php_admin_value` را نمی‌پذیرد.

فرض نکنید `php.ini` مورد استفاده CLI همان فایلی است که Apache یا FPM می‌خواند.

### ۵. اعتبارسنجی و reload

در Apache با ساختار EL7:

```bash
sudo httpd -t
sudo systemctl reload httpd
```

اگر reload پشتیبانی نمی‌شود یا تغییر را اعمال نمی‌کند، پس از بررسی اثر عملیاتی از restart برنامه‌ریزی‌شده استفاده کنید:

```bash
sudo systemctl restart httpd
```

در Debian/Ubuntu:

```bash
sudo apache2ctl configtest
sudo systemctl reload apache2
```

برای PHP-FPM، ابتدا نام دقیق سرویس را پیدا کنید؛ نام سرویس معمولاً شامل نسخه PHP است. پیکربندی را مطابق روش همان توزیع اعتبارسنجی کنید و سپس سرویس درست را reload/restart کنید.

تا زمانی که تست پیکربندی موفق نشده است، سرویس را restart نکنید.

## بررسی نتیجه

### بررسی دستور ثبت‌شده

برای تنظیمات EL7:

```bash
grep -nE '^[[:space:]]*php_admin_value[[:space:]]+session\.upload_progress\.enabled' \
  /etc/httpd/conf.d/php.conf
```

دستور فعال مورد انتظار:

```apache
php_admin_value session.upload_progress.enabled 0
```

### بررسی مقدار مؤثر PHP وب

مهم‌ترین بررسی، مقدار گزارش‌شده توسط PHP در همان محیط وب است. اگر فایل موقت تشخیصی PHP می‌سازید، دسترسی آن را به localhost یا منبع مدیریتی محدود کنید، فقط به‌صورت محلی درخواست بفرستید و **بلافاصله پس از بررسی فایل را حذف کنید**.

محتوای نمونه:

```php
<?php
header('Content-Type: text/plain; charset=utf-8');
echo 'session.upload_progress.enabled=';
var_export(ini_get('session.upload_progress.enabled'));
echo PHP_EOL;
```

این فایل را موقتاً با نامی غیرقابل‌حدس در document root صحیح قرار دهید و دسترسی آن را محدود کنید. بسته به نسخه PHP و نحوه بازگشت مقدار، نتیجه ممکن است `false`، رشته خالی یا نمایش متناظر با `0`/`Off` باشد.

پس از بررسی، فایل را فوراً حذف کنید. صفحه عمومی `phpinfo()` یا endpoint تشخیصی را در دسترس عموم باقی نگذارید.

### بررسی وضعیت سرویس و لاگ‌ها

در EL7:

```bash
sudo systemctl status httpd --no-pager
sudo journalctl -u httpd -n 100 --no-pager
```

در Debian/Ubuntu:

```bash
sudo systemctl status apache2 --no-pager
sudo journalctl -u apache2 -n 100 --no-pager
```

موفقیت `configtest` به‌تنهایی ثابت نمی‌کند که مقدار مؤثر در تمام VirtualHostها یا SAPIها درست است.

## بازگردانی تغییرات

اگر پس از تغییر مشکلی ایجاد شد، بکاپی را که ایجاد کرده‌اید برگردانید. از مسیر دقیق بکاپ استفاده کنید.

نمونه برای EL7:

```bash
sudo cp -a /etc/httpd/conf.d/php.conf.bak.YYYYMMDD-HHMMSS \
  /etc/httpd/conf.d/php.conf
sudo httpd -t
sudo systemctl restart httpd
```

به‌جای `YYYYMMDD-HHMMSS` نام واقعی بکاپ را قرار دهید؛ این عبارت نمونه را عیناً اجرا نکنید.

در توزیع‌های دیگر، فایل درست را بازیابی کنید و از دستور اعتبارسنجی و نام سرویس همان توزیع استفاده کنید.

## سخت‌سازی تکمیلی PHP

اقدام اصلی این مخزن غیرفعال‌کردن session upload progress است. تنظیمات زیر ممکن است افشای اطلاعات یا مصرف بی‌رویه منابع را کاهش دهند، اما **جایگزین patch امنیتی نیستند و CVEهای بالا را رفع نمی‌کنند**.

قبل از تغییر، نیازمندی‌های برنامه را بررسی کنید؛ محدودیت آپلود و زمان اجرا می‌تواند بر عملکرد صحیح برنامه اثر بگذارد.

### غیرفعال‌کردن افشای نسخه PHP

در `php.ini` فعال:

```ini
expose_php = Off
```

این کار افشای نسخه PHP در HTTP headerها را کاهش می‌دهد، اما آسیب‌پذیری‌ها را patch نمی‌کند.

### تعیین محدودیت منطقی برای آپلود و درخواست‌ها

مقادیر زیر صرفاً نمونه اولیه‌اند و باید با نیاز برنامه تطبیق داده شوند:

```ini
file_uploads = On
upload_max_filesize = 50M
post_max_size = 55M
max_file_uploads = 20
max_input_time = 60
max_execution_time = 60
memory_limit = 256M
```

این مقادیر توصیه عمومی برای تمام سرورها نیستند. آن‌ها را بر اساس نیاز برنامه، حافظه در دسترس، اندازه درخواست‌ها و بار کاری انتخاب کنید. اگر آپلود فعال است، معمولاً `post_max_size` باید حداقل به‌اندازه `upload_max_filesize` باشد.

از مقادیر نامحدود یا بیش از حد بزرگ مانند `memory_limit = -1`، `max_execution_time = 0` یا محدودیت‌های چندگیگابایتی آپلود اجتناب کنید، مگر اینکه نیاز عملیاتی مستند و کنترل منابع کافی داشته باشید.

### تنظیمات session

این گزینه‌ها را با توجه به نسخه PHP و سازگاری برنامه بررسی کنید:

```ini
session.use_strict_mode = 1
session.use_only_cookies = 1
session.cookie_httponly = 1
```

اگر برنامه فقط از HTTPS استفاده می‌کند و استقرار شما با آن سازگار است، فعال‌کردن `session.cookie_secure = 1` را نیز بررسی کنید. تغییرات session را قبل از اعمال سراسری در محیط آزمایشی بررسی کنید.

همه تنظیمات را بدون بررسی در محیط production کپی نکنید. پشتیبانی و مقدار پیش‌فرض directiveها بین نسخه‌های PHP متفاوت است؛ پس از هر تغییر، پیکربندی را اعتبارسنجی کنید.

## سیستم‌عامل‌های غیر RHEL و EL7

اسکریپت فعلی عمداً برای خانواده بسته‌های EL7 طراحی شده است و ممکن است روی سیستم‌های دیگر از اجرا صرف‌نظر کند. علت این است که وضعیت CVE و اصلاحات بسته‌ها به vendor وابسته‌اند.

برای سیستم‌عامل‌های دیگر:

1. نسخه دقیق PHP، شماره انتشار بسته و SAPI را شناسایی کنید: Apache `mod_php`، PHP-FPM یا handler دیگر.
2. اطلاعیه امنیتی maintainer سیستم‌عامل را برای همان بسته بررسی کنید.
3. در اولویت، بسته اصلاح‌شده vendor یا نسخه پشتیبانی‌شده PHP را نصب کنید.
4. اگر اطلاعیه امنیتی غیرفعال‌کردن session upload progress را توصیه می‌کند، مقدار `session.upload_progress.enabled = Off` را در پیکربندی SAPI فعال تنظیم کنید.
5. در Apache با `mod_php` می‌توان از `php_admin_value session.upload_progress.enabled 0` در context مناسب Apache استفاده کرد.
6. در PHP-FPM، از روش تنظیم PHP INI یا FPM مورد پشتیبانی همان نسخه استفاده کنید؛ دستور مختص Apache را در فایل FPM قرار ندهید.
7. پیکربندی را اعتبارسنجی کنید، سرویس صحیح را reload کنید و مقدار مؤثر را از محیط وب بررسی کنید.
8. فقط بر اساس شباهت شماره نسخه، یک CVE را «غیرآسیب‌پذیر» اعلام نکنید. اطلاعیه دقیق vendor و اصلاحات backport‌شده را بررسی کنید.

## عیب‌یابی

### اسکریپت سیستم‌عامل را پشتیبانی‌نشده اعلام می‌کند

اسکریپت محافظه‌کارانه عمل می‌کند. این موارد را بررسی کنید:

```bash
cat /etc/os-release
cat /etc/centos-release 2>/dev/null
rpm -q php httpd 2>/dev/null
```

اسکریپت را بدون بررسی فرضیات، مسیرها، کنترل بسته‌ها، SAPI و دستورات سرویس روی سیستم‌عامل نامرتبط اجرا نکنید.

### Apache پیام `Syntax OK` می‌دهد، اما تنظیم وب غیرفعال نیست

علت‌های احتمالی:

- برنامه به‌جای `mod_php` از PHP-FPM استفاده می‌کند.
- تنظیم در فایل اشتباه قرار گرفته است.
- نمونه دیگری از Apache یا درخت پیکربندی دیگری درخواست‌ها را سرویس می‌دهد.
- درخواست به host یا container دیگری می‌رسد.
- تنظیم هنوز در SAPI در حال اجرا بارگذاری نشده است.

SAPI، مسیرهای تنظیمات، سرویس، VirtualHost و مقدار مؤثر وب را بررسی کنید.

### Apache هشدار می‌دهد یک ماژول قبلاً بارگذاری شده است

پیامی مانند `module php5_module is already loaded, skipping` معمولاً به وجود دستور تکراری بارگذاری ماژول اشاره دارد. این پیام با خطای syntax یکسان نیست. محل‌های تکراری `LoadModule` را جداگانه و با احتیاط بررسی کنید؛ بدون مشخص‌شدن فایل معتبر، خطوط بارگذاری ماژول را حذف نکنید.
